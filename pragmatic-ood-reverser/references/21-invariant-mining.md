# 隐式不变式挖掘与胖类拆分信号指南（S2 / S3 核心手册）

> **理论锚点** `[§24.3.7.1, §23.4.3.5]`：
> - “使一个对象的状态定义良好的性质被称为它的不变式（Invariant）。” `[§24.3.7.1]`
> - 存量代码极少像原文 `String::check()` 那样显式写出不变式检查函数；但**不变式依然隐式存在于散落的校验、数据库约束与调用时序中**。若维护者未能逆向还原这些隐式不变式，修改代码时极易破坏对象合法状态而引发线上故障 `[§23.4.6, §24.3.7.1]`。

## 一、挖掘隐式不变式的五类证据源

在逆向分析某个核心类或模块时，按以下 5 个水源依次检索（`grep` / 精读），先记录哪里实施了校验，再搜索旁路写入、批量更新和失败路径。标注局部前置条件、候选不变式或已交叉验证的不变式，不把注解直接当作部署中的 DB 约束。只有授权保存时才更新地图第 5 节。

### 水源 1：构造函数、静态工厂与初始化方法 `[§23.4.3.2, §24.3.7.1]`
- **勘探目标**：原文指出“初始化的作用就是将对象置入一个满足不变式的状态中，这件事通常由构造函数完成” `[§24.3.7.1]`。
- **代码特征**：
  - 构造器内的 `Objects.requireNonNull`、`if (x < 0) throw ...`、Guava `Preconditions`、TS `zod.parse` 或 `asserts` 函数 `[§24.3.7.2]`；
  - 字段默认值赋予与关联计算（例如：`this.remaining = this.total - this.used` 暗示了 `remaining + used == total` 的恒等不变式）。
- **两阶段构造陷阱预警**：若发现某类使用无参构造器 `new Foo()` 创建后，必须在外部按特定顺序调用 `foo.initA()`、`foo.setB()` 才能正常工作，说明该类在构造完成瞬间**并未建立不变式**（标记为 RL10 时序耦合雷区）！

### 水源 2：修改操作（Mutators）入口与出口的条件守卫 `[§24.3.7.1, §24.3.7.3]`
- **勘探目标**：在贫血模型或过程式 Service 中，原本属于实体类的不变式和前/后置条件 `[§24.3.7.3]` 往往外溢到了 `XxxService` 的 `if-else` 分支里。
- **代码特征**：
  - 搜索修改该实体状态的所有位置（`entity.setXxx(...)` 或直接属性赋值）；
  - 提取赋值前的守卫条件（如 `if (order.getStatus() != PAID || order.getRefundedAmount().compareTo(order.getPayAmount()) > 0) throw ...`）；
  - **逆向还原隐式状态机**：将散落在多个 Service 方法里的 `status` 判断与赋值得出有向图，还原出该实体真实的**合法状态迁移图（State Transition Invariant）**。

### 水源 3：持久化 Schema 与序列化约束 `[扩展]`
- **勘探目标**：当业务代码缺乏校验时，数据库表结构或接口 Schema 往往充当了最后一道状态不变式防线。
- **代码特征**：
  - **Java**：JPA `@Column(nullable = false, unique = true, length = ...)`、Bean Validation `@NotNull` / `@Min` / `@Positive`、数据库 Flyway/Liquibase 迁移脚本中的 `CHECK` 与唯一索引约束；
  - **TS**：Prisma `schema.prisma`（如 `@unique`、`@@index`、非 `?` 必填字段）、Drizzle 表定义、以及入口处的 `zod` / `valibot` Schema。
- **不一致风险点**：若数据库字段允许为 `NULL`，但某段业务代码无条件调用 `entity.getXxx().trim()`，立即标记为**“未受保护的隐式非空假设”**。

### 水源 4：单元测试与集成测试断言 `[§23.4.5, §24.3.7.2]`
- **勘探目标**：原文指出断言与测试从另一个角度审视了类的冗余一致性 `[§23.4.5, §24.3.7.1]`。存量测试里的 `assertEquals` / `assertThrows` / `expect(...).toThrow()` 是原作者留下的最直接的“可执行规范说明”。
- **勘探动作**：打开目标类对应的 `*Test.java` 或 `*.test.ts`，重点阅读异常测试分支（测试了哪些非法输入）以及状态修改后的多字段联合断言。

### 水源 5：并发锁与事务边界 `[§25.7.1 · 扩展]`
- **勘探目标**：识别多字段或多实体之间的原子性不变式。
- **代码特征**：检查 `synchronized`、`ReentrantLock`、`@Transactional` 或数据库悲观锁（`SELECT ... FOR UPDATE`）包裹的范围——锁或事务包裹的多步写操作，其首尾之间正是**“不变式暂时失效、退出前必须恢复”**的临界区 `[§24.3.7.1, §25.7.1]`。

## 二、利用不变式与字段访问矩阵识别拆分候选（RL4）

> **理论锚点** `[§23.4.3.5, §24.3.7.1]`：
> - “如果一个类的操作的子集合具有差异显著的使用模式，或者这种子集合访问的总是表示之中不同的子集合，或者这个类常常出现在相互无关的讨论之中等，就说明这个类可能是分裂为两个的候选者。” `[§23.4.3.5]`
> - “对于那些应该分裂的类，将不变式与操作代码比较，将显示出大部分不变式检查是多余的。在这些情况下，操作的某些子集合都只访问对象状态的子集。” `[§24.3.7.1]`

### 逆向解剖四步法（针对 >300 行的核心大类或上帝 Service）

1. **列出状态字段（或被注入的依赖组件）集合 $F$**：
   - 对实体类：列出所有内部字段 $\{f_1, f_2, \dots, f_n\}$；
   - 对无状态的上帝 Service：将其持有的 Repository / 外部 Client 视为它的“依赖状态集” $\{d_1, d_2, \dots, d_m\}$。
2. **构建“方法 × 字段/依赖”访问矩阵**：
   - 快速扫描类内公开方法，标记每个方法实际读写了哪些字段（或调用了哪些注入依赖）。
3. **识别对角块聚类（Block-Diagonal Clustering）**：
   ```text
   示例：800 行的 Order 类访问矩阵
                 [id, status]  [items, coupon, payAmt]  [receiver, address, trackingNo]  [invoiceTitle, taxNo]
   addItem/pay        RW                 RW                           -                            -
   ship/updateAddr    R                   -                          RW                            -
   issueInvoice       R                   R                           -                           RW
   ```
   - 矩阵提示计费、物流、开票三个候选职责；`issueInvoice` 仍读取计费字段。这是需验证的交叉依赖，不是三个互不相交的证明。
4. **验证不变式正交性并输出结论**：
   - 检查这几个聚类块的不变式是否彼此独立（例如：`trackingNo` 的格式校验与 `coupon` 折扣计算毫无关系）；
   - 在对话或地图第 4/7 节记录矩阵、共享字段与反例。移交 R0 时说明哪些修改可能隔离、哪些仍须联合回归；不要把聚类直接当成重构决定 `[§23.4.3.5]`。
