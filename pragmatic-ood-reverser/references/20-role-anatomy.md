# 七类角色的逆向识别与“名实不符”伪装图鉴

> **逆向剖析核心立场** `[§25.1]`：存量代码中的语法关键字（`class`、`interface`、`@Service`、`@Entity`）往往掩盖了类在架构中实际扮演的角色。逆向理解一个组件时，必须穿透语法表象，还原每个核心类的**真实架构角色（7 种类的作用）**，并敏锐识别**“名实不符”的伪装反模式**。

---

以下是选读线索，不是按行数、依赖数或接口实现数给类定性。先查调用方、具体行为与反例；七角色可以交叠，也可不适用。设计动机只能标为推断。

## 一、 语法表象 vs 真实角色 vs 常见伪装总表

| 存量代码表象 | 理想角色 `[§25.1]` | 常见“名实不符”伪装（反模式） | 逆向识别信号（代码证据特征） |
|---|---|---|---|
| `@Entity` / Prisma Model / `XxxDO` / `XxxVO` | **具体类型** `[§25.2]` 或 **结点类** `[§25.4]` | **公用可变数据袋（Anemic Data Bag）**`[§24.2.1, §24.4.2]` | 全字段暴露 `public setter`（或 TS 无 `readonly` 可变属性），无任何不变式校验，生命周期内任意时刻可处于半合法状态 |
| `XxxService` / `XxxManager` / `XxxHelper` / `XxxProcessor` | **组件门面（界面类）**`[§25.6]` 或 **动作协调** `[§25.5]` | **过程式功能分解巨兽（Procedural God Class）**`[§24.2.1]` | 类本身无业务状态，注入 6+ 个外部 Repository/Service，方法长达百行，频繁 `get` 出实体字段做计算再 `set` 回去 |
| `IXxxService` + 唯一 `XxxServiceImpl` | **抽象类型** `[§25.3]` | **投机性伪抽象（Speculative 1:1 Interface）**`[§23.4.3.4]` | 接口与实现类方法 1:1 机械镜像，签名直接暴露底层 ORM/框架类型，全库既无第二种实现也无测试替身 |
| 顶层基类/接口含大量空方法或抛 `UnsupportedOperationException` | **抽象类型** `[§25.3]` 或 **结点类** `[§25.4]` | **肥大的界面（Fat Interface）**`[§24.4.3]` | 子类被迫空实现或抛异常；调用方附近伴随 `instanceof` / 类型强转或捕获“不支持操作”异常 |
| 含 `type/status` 枚举 + 10 余个可空专属字段的大类 | **结点类层次** `[§25.4]` 或 **封闭变体集** (P21) | **内嵌类型域的未分裂胖类** `[§23.4.3.5, §24.3.4.1]` | 类内不同 `switch(type)` 分支只读写各自那几个字段，任意实例总有一半以上字段为无意义的 `null` |
| 继承自具体类（如 `VipUser extends NormalUser`、`MyList extends ArrayList`） | **屏蔽子类型的组合复用** (P10 `[§24.3.4]`) | **为省代码而滥用公用派生** `[§24.3.4, §25.2.1, §25.9[5]]` | 派生类并不完全满足基类不变式，或基类本是具体类型（无多态设计意图），导致外部可通过向上转型绕过子类约束 |

## 二、 七种角色逆向解剖指南（S2 活动执行手册）

### 1. 具体类型（Concrete Types）逆向识别 `[§25.2, §25.2.1]`
- **正向特征**：代表相对简单的独立概念（如金额、日期区间、坐标、配置项、紧凑容器），界面与实现一对一绑定，极少依赖其他类即可独立理解 `[§25.2]`。
- **逆向勘探看点**：
  1. 它是否做到了封装表示（无裸露可变字段 P04）、并维护了清晰的**状态不变式**（P20 `[§24.3.7.1]`）？
  2. **危险信号 A（从具体类派生）**：检查是否有其他类 `extends` 了这个具体类型 `[§25.2.1, §25.9[5]]`——若有，重点排查子类是否破坏了父类的不变式（L3）。
  3. **危险信号 B（过度虚化，`Date2` 反例）**：检查是否把本该紧凑独立的具体类型做成了全虚函数 + `protected` 字段的复杂基类 `[§25.2.1]`。

### 2. 抽象类型（Abstract Types）逆向识别 `[§25.3]`
- **正向特征**：纯界面契约（Java `interface` / TS `interface` 或纯抽象类），将使用者与具体实现类（如 `List_set`、`Vector_set`）彻底解耦 `[§25.3]`。
- **逆向勘探看点**：
  1. **实现普查**：在代码库中搜索该接口的所有实现类（`implements`）——是真正存在多个共存实现（或外部网关隔离、单测 Mock），还是毫无意义的 1:1 机械接口 `[§23.4.3.4]`？
  2. **实现泄漏检查**：接口方法的参数与返回值是否夹带了特定实现才有的细节（例如集合接口暴露了数组下标，或仓储接口暴露了 `Pageable` / Prisma 专有查询参数 `[§24.4.2, §25.3]`）？

### 3. 结点类（Node Classes）逆向识别 `[§25.4, §25.4.1]`
- **正向特征**：处于继承树中（`Vehicle -> Car -> Ambulance`），既依赖基类的表示与基础服务，又向用户暴露比基类更宽的界面（新增特有方法）`[§25.4]`。
- **逆向勘探看点**：
  1. **上下游耦合度**：结点类只有在所有直接与间接基类的语境下才能理解 `[§25.4]`。逆向阅读时必须**自顶向下串联整条继承链**，切忌只看单个子类文件。
  2. **反向依赖与脆弱基类风险** `[§24.3.2.1]`：检查基类的非虚方法调用了哪些可覆盖方法（虚钩子），以及暴露了哪些 `protected` 字段——若子类覆写方法时未遵守基类的隐式约定，就会引发诡异的运行时 Bug。
  3. **运行时窄化点**：搜索全库对该层次结构使用 `instanceof` / 类型守卫的位置 `[§25.4.1]`，识别哪些地方依赖了子类拓宽的特有界面。

### 4. 动作类（Action Classes）逆向识别 `[§25.5]`
- **正向特征**：将需要延迟执行、携带状态、排队重试、撤销或跨进程传输的“动词”封装为对象（如 `Command`、`Job`、`EventHandler`、组合符）`[§25.5]`。
- **逆向勘探看点**：
  1. 找出动作对象的**创建点（捕获了哪些上下文状态）**与**触发执行点（何时何地调用 `execute/do_it`）**，还原异步/延迟控制流。
  2. **功能分解退化警示** `[§25.5]`：如果发现系统里几乎每个业务操作都被写成了无状态的 `XxxAction` / `XxxHandler`，且操作的数据全是外部传入的贫血对象，说明该系统实质上是披着 OO 外衣的过程式架构 `[§24.2.1, §25.5]`。

### 5. 界面类（Interface Classes，即适配器/包装器）逆向识别 `[§25.6, §25.6.1]`
- **正向特征**：本身代码极薄，仅用于转换接口签名、消解命名冲突、调整下标/单位偏移、附加范围检查（`Range`）或隔离外部库/遗留 C 代码 `[§23.5.4, §25.6, §25.6.1]`。
- **逆向勘探看点**：
  1. 在 S1/S2 绘图中，将纯界面类标记为**“薄适配/防腐层”**，帮读者一眼看穿“它背后真正干活的被包装类是谁”。
  2. **职责越界警示**：检查原本作为薄适配器的类（如 Controller、Server Action、SDK Wrapper）是否偷偷塞入了大段核心计费或状态流转逻辑 `[§25.6]`。

### 6. 句柄类（Handle Classes，含代理与切面控制器）逆向识别 `[§25.7, §25.7.1]`
- **正向特征**：持有指向实际表示（`rep`）的引用，接管生命周期、支持运行期动态重绑定（`bind`），或在转发操作前后织入并发锁、事务、缓存与访问统计（如 `Set_controller`）`[§25.7, §25.7.1]`。
- **逆向勘探看点**：
  1. **识别隐式切面**：在 Java（Spring `@Transactional`、`@Async`、动态代理）或 TS（高阶包装函数、ES `Proxy`、中间件）中，句柄往往是**隐式织入**的。逆向走查时必须标出代理边界，否则会漏掉事务提交、锁竞争或异常回滚逻辑。
  2. **锁粒度检查** `[§25.7.1]`：检查并发控制器是否对所有只读探查方法也一刀切加了互斥锁，定位潜在的并发瓶颈。

### 7. 应用框架（Application Frameworks）与业务边界解剖 `[§25.8 · 扩展]`
- **正向特征**：框架掌控主循环（`main_loop`）与顶层异常处理，业务代码实现钩子被框架回调（好莱坞原则）`[§25.8]`。
- **逆向勘探看点**：
  1. 识别存量系统是否在内部自研了某种“小型插件框架/流水线引擎”（如自定义 `AbstractJobFilter`）——若有，优先画出其 `main_loop` 主干控制流与钩子调用顺序 `[§25.8]`。
  2. 评估业务领域类受外部框架（Spring / Next.js）侵蚀的程度（详见语言逆向文件 `50` 与 `51`）。
