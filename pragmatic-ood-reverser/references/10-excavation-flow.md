# 勘探活动执行手册

档位、权限、恢复以 [SKILL.md](../SKILL.md) 为准；以下是每个活动的取证与退出条件。只读模式的“产物”均在对话中给出，章节号对应可选的地图模板。

<a id="triage"></a>

## T · 定范围

辨认目标进程的源码根、入口、构建声明与用户改动目标。Java 查 Maven/Gradle（含 Kotlin DSL）；TS 查 `package.json`、`tsconfig`、服务端入口，不把同仓 UI 或多个部署当成一个单体。若只拿到一个文件，报告局部观察并列出需要补看的调用方。已有地图先按主文的恢复协议复核。退出：目标与可用证据范围已明确，或明确为何只能抽样。

<a id="S0"></a>

## S0 · 只读物理测绘 `[§23.4.4]`

1. 用主文命令扫描目标目录（TS 若依赖 paths，优先选包含 `tsconfig.json` 的项目根，而不是它下方的 `src`），读 stdout、stderr 和退出状态；不在目标目录生成报告或缓存。脚本按目录/物理包推测组件，排除常见测试/构建目录，不能识别全部生成代码或区分前后端。需要测试、迁移证据时单独阅读。
2. 记录语言、根、排除项、文件数，以及未纳入静态图的引用数量与典型位置。混合目录默认各出一份报告；需要聚焦时显式指定语言。空结果或失败不能记为零依赖。
3. 读每个强连通分量的**成员集合**，从跨组边表核对方向、导入种类、文件和行；不要将成员顺序画成路径。模块级的相互依赖也不必然构成文件级环。TS 对照值候选图与含类型声明的图；内联全类型的导入单独标记 `inline-type`，可能保留空导入副作用，需看编译配置，Java 注意同包引用、反射、Bean 装配不会完整出现。
4. 选与用户目标相关的一处入口和一处热点精读。若脚本无法执行，手查构建、目录与数个 import 作为明确标注的样本，不编造 SCC 或度数。退出：有范围说明和可定位的首批线索（地图第 1 节）。

<a id="S1"></a>

## S1 · 由物理目录还原业务组件 `[§24.3.1, §24.4]`

将领域概念、框架入口、实现细节分开；折叠样板不代表不读它。若规则在 SQL/配置/中间件，就把它带回链路。水平分层项目按入口、数据和共同职责提出逻辑分组，用公开界面与内部实现的具体调用验证。图例区分「导入」「实际调用」「事件/推断」；不要把文件夹名当作领域边界。退出：读者能从一个入口到达焦点组件，知道哪些跨边界关系尚不确定（第 2–3 节）。

<a id="S2"></a>

## S2 · 概念、角色和字段矩阵 `[§23.4.3.1, §23.4.3.5, §25.1]`

选择少数真正影响用户问题的核心类型或函数。用业务语言命名概念，比较语法形态与实际职责；七角色是解释工具，不要求 TS 函数或每个 DTO 都套一个类角色。若方法群反复访问互斥的字段/依赖，列方法 × 字段矩阵，并检查共享约束与例外。代码体积只能选样，不能单独证明需要拆类。退出：有能被源码支持或反驳的概念解释（第 4 节）。

<a id="S3"></a>

## S3 · 约束与用例走查 `[§23.4.3.1, §24.3.7.1]`

从入口追到状态修改、持久化和外部副作用；变更评估还要找一条反向写入、异常/回滚或消息消费路径。区分「源码允许」「守卫拒绝」「测试覆盖」「部署中实际发生」。检查构造、守卫、迁移、测试和事务；记录交叉印证及反例。对仅见于单一写入点的规则先标局部前置条件，而非全局不变式。新增隐式边要回补 S1。源码和测试都无法说明的历史原因列为待验证 `M-xxx`，不阻塞其余走查。退出：用户知道改哪里、哪些约束有证据、还要验证什么（第 5、6、9 节）。

<a id="S4"></a>

## S4 · 修改指南与 R0 `[§23.4.6, §23.7[36], §23.7[37]]`

用“修改目标 → 相对低风险的扩展点及成立条件 → 波及的消费者 → 回归检查”作结。区分已跑测试与建议测试；低入度、单一实现或未检出环不构成安全证明。每条诊断同时给证据、善意假设、风险条件和避坑建议（第 7–8 节）。用户准备重构时提供第 10 节：目标边界、拆分候选与反证、必须保持的可验证不变式、未解问题。没有 `pragmatic-ood-architect` 也能独立使用此移交单，不自动启动下一项任务。
